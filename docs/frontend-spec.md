# Спецификация frontend Bid CRM

## 1. Цель и границы

Сделать компактный интерфейс CRM для авторизованных сотрудников: быстрый список
сделок с поиском, фильтром и серверной пагинацией, понятным запуском синхронизации
с внешней CRM, а также страницы входа, регистрации и восстановления пароля.

Визуальный ориентир — Bitrix24: рабочая оболочка с боковой навигацией, ясной
иерархией и плотным списком данных. Не переносить сложность Bitrix24: на первом
этапе оставить только сделки, профиль и выход.

Документ фиксирует целевое поведение. Указанные ниже поиск и синхронизация требуют
изменений backend и OpenAPI: сейчас соответствующих контрактов нет.

## 2. Результаты анализа backend

### Что уже работает

- Стек: Laravel 13, PHP 8.3+, Inertia 3, React 19, TypeScript, Tailwind CSS 4.
- Ant Design 6, `openapi-fetch` и `openapi-typescript` уже есть в зависимостях.
- API описан в [openapi/openapi.yaml](../openapi/openapi.yaml); типы генерируются
  командой `npm run openapi:generate` в
  [resources/js/generated/api.d.ts](../resources/js/generated/api.d.ts).
- REST-клиент на `openapi-fetch` и отправка заголовка `X-XSRF-TOKEN` реализованы в
  [resources/js/lib/api.ts](../resources/js/lib/api.ts). Клиент использует
  `credentials: include`, но сам не запрашивает CSRF-cookie.
- API авторизации: `GET /api/auth/csrf-cookie`, `POST /api/auth/register`,
  `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/user`,
  `POST /api/auth/forgot-password`, `POST /api/auth/reset-password`.
- Сделки защищены сессионной авторизацией. `GET /api/deals` поддерживает фильтр
  `status`, сортировку, `page` и `per_page` (максимум 100; размер по умолчанию
  15). Ответ — Laravel resource collection с `data`, `links`, `meta`.
- Статусы: `NEW`, `IN_PROGRESS`, `WON`, `LOST`. DTO сделки содержит `id`,
  `external_id`, `title`, `status`, `amount`, `external_updated_at`,
  `external_version`, ID автора/ответственного и временные метки.
- На web-стороне пока зарегистрирована только страница `/` (`welcome`). Страниц
  входа и списка сделок, равно как и web-маршрутов `/login` и `/deals`, пока нет.

### Backend-ограничения, которые влияют на UX

1. Текстовый поиск не принимается: `IndexDealsRequest` и `DealFilter` умеют только
   фильтр по статусу. Поиск по названию/внешнему ID нельзя имитировать фильтрацией
   уже загруженной страницы — результаты будут неполными.
2. Нет endpoint для запуска синхронизации, статуса фоновой задачи или сведений о
   подключённой CRM. Поля `external_updated_at` и `external_version` описывают
   данные сделки, но не доказывают, что доступна команда обновления.
3. API списка пользователей возвращает профиль текущего пользователя, а не
   справочник сотрудников. Поэтому ID ответственного пока нельзя достоверно
   отобразить как имя.
4. Страница сделки не определена. Карточка списка не должна выглядеть как ссылка
   на несуществующий маршрут.

## 3. Технологии и границы библиотек

- React + TypeScript, Inertia для страниц и навигации Laravel.
- Ant Design 6 — единственный runtime UI kit: `ConfigProvider`, `Layout`,
  `Menu`, `Input`, `Select`, `Card`, `Tag`, `Button`, `Alert`, `Skeleton`,
  `Pagination`, `Form`, `Input.Password`, `Typography` и `Space`.
- DaisyUI использован как источник семантических принципов и проверенных паттернов
  состояний (base / primary / success / warning / error; card / badge / alert /
  skeleton), но пакет DaisyUI в проект не добавлять и Daisy-классы с Ant Design
  не смешивать. Это сохраняет один набор компонентных стилей и избегает
  конфликтующих reset/theme правил.
- API-вызовы — только через типизированный `openapi-fetch`-клиент. Не создавать
  второй незащищённый `fetch`-клиент для тех же endpoint.
- При изменении контракта сначала обновлять OpenAPI и backend, затем выполнять
  `npm run openapi:generate`; сгенерированный `api.d.ts` вручную не редактировать.
- Wayfinder использовать для Laravel web-маршрутов и Inertia-ссылок после их
  генерации. REST API адреса и типы брать из OpenAPI, а не дублировать URL в UI.

## 4. Информационная архитектура и маршруты

| URL | Доступ | Назначение |
| --- | --- | --- |
| `/login` | Гость | Вход |
| `/register` | Гость | Регистрация |
| `/forgot-password` | Гость | Запрос письма для сброса пароля |
| `/reset-password?token=…&email=…` | Гость | Установка нового пароля |
| `/deals` | Авторизованный пользователь | Список сделок |

Laravel должен отдавать Inertia-страницы для этих маршрутов. Гостевой заход на
`/deals` перенаправляет на `/login`; авторизованный заход на auth-страницы
перенаправляет на `/deals`. Проверка frontend-состояния не заменяет серверную
защиту маршрутов и API.

Внутри CRM оболочки на первом этапе:

- сайдбар: логотип/название, «Сделки» (активный пункт), компактный блок профиля;
- верхняя панель: заголовок раздела и меню пользователя с выходом;
- рабочая область: заголовок «Сделки», поиск, статусный фильтр, кнопка обновления,
  карточки и серверная пагинация.

Не добавлять в навигацию несуществующие разделы, фиктивные счетчики, создание
сделки, редактирование, канбан, массовые операции или профиль сотрудника.

## 5. Основные пользовательские потоки

### 5.1. Вход в CRM

1. Пользователь открывает `/login`.
2. Клиент инициализирует сессию запросом `GET /api/auth/csrf-cookie`; браузер
   сохраняет cookie.
3. Пользователь вводит email и пароль, отправляет форму.
4. Клиент читает `XSRF-TOKEN`, URL-декодирует его и отправляет значение в
   `X-XSRF-TOKEN`. Cookie сессии отправляется браузером автоматически.
5. При `200` сервер ротирует сессию; пользователь переходит на `/deals`.
6. При `422` показывается ошибка рядом с полем email (не раскрывать, существует
   ли аккаунт, кроме ожидаемого общего сообщения об ошибке входа).
7. При `419` показать понятное сообщение об истёкшей защите сессии, заново
   получить CSRF-cookie и предложить отправить форму повторно.
8. При сетевой/серверной ошибке сохранить введённый email, не сохранять пароль,
   показать retry без сброса формы.

### 5.2. Регистрация

1. Пользователь переходит с формы входа по ссылке «Создать аккаунт».
2. Заполняет имя, фамилию, email, пароль и подтверждение.
3. Клиент предварительно получает CSRF-cookie, если действительной cookie нет.
4. Отправляет `POST /api/auth/register`; успешный `201` означает, что сервер
   создал пользователя и авторизовал сессию.
5. При успехе перейти на `/deals`; при `422` показать серверные ошибки у полей.
6. Не очищать поля, не затронутые ошибками; очищать пароль и подтверждение после
   успешной регистрации.

### 5.3. Восстановление и сброс пароля

1. Ссылка «Забыли пароль?» открывает `/forgot-password`.
2. Пользователь вводит email; после CSRF-инициализации отправляется
   `POST /api/auth/forgot-password`.
3. Для любого корректного email показывать одинаковый текст: если адрес
   зарегистрирован, письмо со ссылкой будет отправлено. Не показывать наличие
   аккаунта.
4. Переход из письма открывает `/reset-password` с `token` и `email`.
5. Форма отправляет email, token, пароль и подтверждение в
   `POST /api/auth/reset-password`; ошибки токена/валидации показываются без
   раскрытия внутренних деталей.
6. После успешного сброса показать подтверждение и ссылку на вход.

### 5.4. Поиск и просмотр списка сделок

1. При открытии `/deals` страница загружает `GET /api/auth/user`; при `401`
   серверная/Inertia-логика отправляет пользователя на `/login`.
2. Затем клиент запрашивает первую страницу `GET /api/deals?per_page=15`.
3. Пользователь вводит поисковую фразу или выбирает статус.
4. Изменение поискового запроса или статуса сбрасывает `page` в `1`; поисковая
   фраза применяется с debounce около 300 мс. Enter применяет её немедленно.
5. Запрос передаёт активные фильтры, страницу и размер страницы в API. URL
   страницы синхронизируется с фильтрами так, чтобы ссылку можно было открыть и
   обновить без потери состояния.
6. Пользователь меняет страницу; сохраняются поиск и статус.
7. Очистка фильтров возвращает список к первой странице и исходному состоянию.
8. Смена фильтра отменяет/игнорирует предыдущий незавершённый запрос; поздний
   ответ не должен перезаписать актуальные результаты.

**Backend-условие:** до реализации шага 3 добавить параметр `search` в
`GET /api/deals`. Рекомендованная семантика: trim строки, длина 1–100 символов,
частичное совпадение без учёта регистра по `title` и `external_id`. Параметр
добавить в OpenAPI, валидацию, `DealFilter` и тесты. Не фильтровать данные только
на клиенте.

### 5.5. Обновление из внешней CRM

1. Пользователь нажимает «Обновить из внешней CRM».
2. Кнопка сразу блокируется от повторного нажатия; UI показывает состояние
   запуска только после того, как API подтвердил приём задачи.
3. Принятый запрос показывает неблокирующий баннер «Обновление запущено» и
   доступное продолжение работы со списком.
4. Пока задача выполняется, показывать прогресс только если backend возвращает
   достоверные данные. Иначе использовать неопределённый индикатор без выдуманного
   процента. Запретить запуск второй задачи для того же пользователя/подключения.
5. По завершении показать success-сообщение с количеством добавленных/обновлённых
   записей, если API возвращает эти значения, затем обновить текущую страницу
   списка с сохранёнными фильтрами.
6. При ошибке оставить список доступным, показать краткое безопасное объяснение
   и кнопку повтора. Не показывать stack trace, токены и внутренние ответы CRM.
7. Состояние синхронизации должно восстанавливаться после перезагрузки страницы,
   если задача ещё активна.

**Backend-условие:** синхронизация сейчас не реализована. До включения активной
кнопки нужны подключение/настройки CRM, очередь и endpoint запуска/проверки
задачи. Рекомендуемый контракт:

- `POST /api/deals/sync` — авторизованный CSRF-защищённый запуск, ответ `202` с
  `data.id`, `data.status` (`queued` или `running`) и `data.started_at`.
- Если задача уже выполняется — вернуть активную задачу, а не создать дубль
  (например, `409` с её идентификатором или `202` с тем же ID).
- `GET /api/deals/sync/{sync}` — состояние (`queued`, `running`, `succeeded`,
  `failed`), временные метки и безопасный summary (`created`, `updated`,
  `skipped`). Ошибка должна содержать пользовательский код/сообщение без
  чувствительных деталей.
- Реализация должна ограничивать повторные запуски, переживать сетевые повторы и
  проверять, что пользователь имеет доступ к выбранному подключению.
- Пока контракт и подключение не готовы, кнопку либо не показывать, либо
  показывать отключённой с ясной причиной. Не симулировать успешную синхронизацию.

### 5.6. Выход и истечение сессии

- Выход — `POST /api/auth/logout` с CSRF-заголовком; после `204` очистить локальное
  состояние пользователя и открыть `/login`.
- `401` при загрузке/работе защищённой страницы означает истёкшую сессию: очистить
  пользовательские данные и показать вход, а не пустой экран.
- Не запускать каскад повторных запросов и не отправлять мутирующий запрос
  автоматически повторно при `419`.

## 6. Структура списка и карточка сделки

### Заголовок и элементы управления

- Заголовок «Сделки» и компактное пояснение/счетчик, только если `meta.total`
  присутствует.
- Поиск: placeholder «Название или ID сделки», кнопка очистки; минимальная ширина
  на desktop около 280 px.
- Статус: «Все статусы», «Новая», «В работе», «Выиграна», «Проиграна».
- Кнопка синхронизации располагается справа от фильтров и имеет состояния из
  раздела 5.5.
- При наличии активных фильтров показывать «Сбросить фильтры».

### Карточка

Каждая запись — компактная карточка со следующей иерархией:

1. Название сделки — главный текст, допускает перенос и не обрезается без
   доступного полного значения.
2. Статус — текстовый Tag с цветом и/или иконкой; смысл не передавать только
   цветом.
3. Сумма — форматировать локалью пользователя и валютой, только если валюта
   определена backend-контрактом. Сейчас поле `amount` не содержит валюты, поэтому
   валютный знак не угадывать; форматировать как десятичную сумму и отметить
   валюту как открытый вопрос.
4. Внешний ID — показывать вторичным текстом, только если он есть.
5. Дата обновления — использовать `updated_at`; `external_updated_at` обозначать
   отдельно как время обновления данных внешней CRM.
6. Ответственного показывать только при наличии API-справочника пользователей;
   до этого не выводить сырой ID как имя.

Карточка не кликабельна, пока не существует согласованного маршрута деталей.
Расположение: один столбец на узком экране, компактная сетка/список на широком;
не использовать тяжёлые изображения и анимации.

### Статусы

| API | Подпись | Семантика |
| --- | --- | --- |
| `NEW` | Новая | info |
| `IN_PROGRESS` | В работе | warning |
| `WON` | Выиграна | success |
| `LOST` | Проиграна | нейтральный/ошибка, без избыточного красного акцента |

Цвета и подписи централизовать в одном типизированном mapper, а не размножать
условия в карточках и фильтрах.

## 7. Состояния и обработка ошибок

Для каждого запроса должны быть определённые loading / success / empty / error
состояния:

- **Первичная загрузка:** скелетоны карточек фиксированной высоты; не показывать
  пустое состояние до ответа.
- **Фоновое обновление/фильтр:** сохранять прежние карточки, показывать небольшой
  индикатор загрузки; избегать мерцания всей страницы.
- **Нет сделок:** объяснение и CTA зависят от наличия сценария создания. Поскольку
  API create существует, но UI создания не входит в текущий scope, не выводить
  нерабочую кнопку.
- **Нет совпадений:** текст «По заданным условиям сделки не найдены» и действие
  «Сбросить фильтры».
- **Ошибка списка:** inline Alert с действием «Повторить»; не подменять ошибку
  пустым массивом.
- **Ошибка API:** использовать безопасные `message`/`errors` JSON-ответа;
  `422` привязывать к полям, `401` — к сессии, `419` — к CSRF, `429` — сообщить о
  частых запросах и времени ожидания при наличии `Retry-After`, `5xx` — дать
  retry и не показывать внутренний текст.
- **Синхронизация:** отдельные состояния idle / submitting / queued / running /
  succeeded / failed; success и error остаются видимыми достаточное время и
  доступны для чтения screen reader.

## 8. Дизайн-система

### Принципы

- Чистая рабочая поверхность, компактная плотность и синий акцент в духе
  Bitrix24 без декоративных градиентов, насыщенных фонов и избыточных метрик.
- Основной фон — светлый нейтральный; карточки — белые; границы и вторичный текст
  нейтральные; primary используется для главного действия/активной навигации.
- Смысловые цвета: info для новой сделки, warning для работы, success для
  выигранной/успешной синхронизации, error для ошибки. Цвет всегда дополняется
  подписью/иконкой.
- Размеры базовой сетки: шаг 4/8 px; радиус контролов 6–8 px; карточек 8–12 px;
  тени минимальные; типографика без более чем 3 уровней заголовков.
- Единая конфигурация Ant Design `ConfigProvider`: `colorPrimary`, `colorBgLayout`,
  `colorBgContainer`, `colorText`, `colorTextSecondary`, `colorBorder`,
  `borderRadius`, `controlHeight`, `fontFamily`. Не задавать разные токены
  локально в каждом компоненте.
- Тема по умолчанию светлая. Тёмную тему не включать в первую версию без отдельного
  решения по контрасту и проверок всех статусов.

### Responsive поведение

- Desktop: фиксированный компактный сайдбар и горизонтальная панель фильтров.
- Tablet: сайдбар сворачивается до иконок; фильтры переносятся на следующую строку.
- Mobile: навигация становится drawer, фильтры складываются вертикально, карточка
  показывает статус/сумму без горизонтального скролла; пагинация остаётся
  доступной.
- Целевой минимум интерактивной зоны — 40×40 px; видимый focus ring обязателен.

### Повторно используемые UI-компоненты

- `AppShell` / `AuthLayout`: общие layout-границы и точки адаптации.
- `PageHeader`: заголовок, описание и primary actions.
- `DealSearch`, `DealStatusFilter`, `DealCard`, `DealList`, `DealPagination`.
- `SyncButton`, `SyncStatusBanner`: одна машина состояний для текста, иконки,
  disabled/loading и доступного объявления.
- `FormFieldError`, `AuthForm`, `InlineError`, `EmptyState`, `LoadingSkeleton`.

## 9. Разделение UI и логики

Предлагаемые границы в существующем `resources/js`:

- `pages/`: только сборка страницы, чтение Inertia props и layout.
- `features/auth/`: формы и auth-flow, валидация/ошибки формы, обработчики
  логина/регистрации/сброса.
- `features/deals/`: типизированные модели представления, mapper статуса, hooks
  загрузки списка, URL-состояние фильтров и состояние sync.
- `components/`: переиспользуемые view-only компоненты, принимающие props и
  callbacks; без прямых сетевых запросов.
- `lib/api.ts`: общий OpenAPI-клиент, CSRF bootstrap и единая нормализация
  транспортных ошибок.
- `generated/api.d.ts`: только генерация из OpenAPI.

Компоненты не должны напрямую читать cookie или самостоятельно строить URL.
Хуки/сервисы возвращают данные и действия; компоненты отвечают за отображение.
Страницы не должны содержать бизнес-правила фильтрации и преобразования статусов.

## 10. Безопасность CSRF и сессии

1. Для входа, регистрации, сброса пароля, выхода, синхронизации и любых других
   изменяющих запросов сначала обеспечить наличие актуального CSRF-cookie через
   `GET /api/auth/csrf-cookie`.
2. Перед каждым небезопасным методом (`POST`, `PUT`, `PATCH`, `DELETE`) клиент
   берёт `XSRF-TOKEN` из cookie, URL-декодирует значение и отправляет его в
   `X-XSRF-TOKEN`. Cookie сессии передаётся через `credentials: include`.
3. Использовать только same-origin cookie-based session. Не переносить session
   cookie/CSRF-токен в `localStorage`, `sessionStorage`, URL, логи или аналитику.
4. Пароли не сохранять в состоянии приложения после завершения формы; не логировать
   тела auth-запросов.
5. При `419` обновить CSRF-cookie и сообщить пользователю о необходимости повтора.
   Не повторять автоматически mutating-запрос без idempotency-контракта.
6. Logout инвалидирует сессию на сервере; frontend после успешного ответа очищает
   только клиентский cache, но не пытается самостоятельно «удалить» HttpOnly cookie.
7. В production серверная cookie сессии должна быть `HttpOnly`, `Secure` при HTTPS,
   `SameSite` по архитектуре развертывания; CORS/credentials не расширять до
   wildcard-origin.
8. Ограничения частоты login/register уже есть; UI должен корректно отображать
   `429`, а не бесконечно повторять запрос.

## 11. Производительность и надёжность

- Список всегда загружается серверными страницами. Начальный `per_page` —
  15 (backend default); не запрашивать сразу все записи.
- Поиск debounce 300 мс; статусы отправляются только по фактическому изменению.
- Отменять устаревшие запросы через `AbortSignal` или игнорировать их результат
  по request key; фильтры и страница формируют единый ключ запроса.
- Сохранять карточки при смене параметров до получения нового ответа; применять
  skeleton только при первой загрузке.
- Не выполнять polling постоянно. Для активной синхронизации опрашивать endpoint
  примерно раз в 2–3 секунды, ограничить период и прекратить polling при
  завершении, ошибке, уходе со страницы или неактивной вкладке. Интервал можно
  увеличить при долгом ожидании.
- Кэшировать только данные, которые безопасно переживают повторное чтение; очищать
  пользовательский кэш при logout/401. Не хранить password, csrf token или
  session cookie в кэше приложения.
- Карточки не требуют виртуализации при лимите 100 записей; не добавлять
  виртуализатор до измерения реальной проблемы.
- Не загружать большие изображения, графики или UI-пакеты, не нужные странице.

## 13. Критерии приёмки

- Неавторизованный пользователь не может загрузить `/deals` или `GET /api/deals`;
  после входа и обновления страницы сессия остаётся рабочей.
- Все изменяющие запросы включают CSRF-заголовок; CSRF bootstrap выполняется до
  первого auth/write-запроса; токены/пароли не сохраняются в web storage.
- Вход, регистрация, запрос сброса и установка нового пароля показывают
  validation/loading/success/error состояния и корректно обрабатывают `401`,
  `419`, `422`, `429` и сетевой сбой.
- Список передаёт status, search, page и per_page серверу; переключение фильтра
  сбрасывает страницу; пагинация сохраняет фильтры; устаревший ответ не
  перезаписывает актуальный.
- Пустой список, отсутствие результатов, ошибка и первичная загрузка различимы и
  не представлены одинаковым пустым экраном.
- Синхронизация показывает «запущено», «успешно» и «ошибка» только по серверному
  состоянию, блокирует дублирующий запуск и позволяет продолжить пользоваться
  списком. Пока sync API отсутствует, интерфейс не сообщает о фиктивном запуске.
- Карточки корректно показывают каждый статус, decimal amount, отсутствующий
  external ID и временные метки без сырых ID ответственных.
- Основные сценарии доступны с клавиатуры, ошибки связаны с полями формы,
  контраст/фокус достаточны, а цвет статуса дублируется текстом.
- Поиск не делает запрос на каждый введённый символ, первая загрузка не скачивает
  все сделки, повторный запрос не создаёт лишнюю синхронизацию.
